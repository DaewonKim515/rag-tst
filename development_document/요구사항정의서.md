# 문서 기반 RAG 시스템 요구사항 정의서

## 1. 문서 개요

| 항목 | 내용 |
|---|---|
| 문서명 | 문서 기반 RAG(Retrieval-Augmented Generation) 시스템 요구사항 정의서 |
| 문서 버전 | v1.0 |
| 작성일 | 2026-07-27 |
| 대상 시스템 | `document` 폴더 내 PDF 및 기타 문서를 읽고 답변하는 RAG 시스템 |
| 문서 목적 | 시스템의 범위, 기능, 품질 기준, 제약사항 및 검수 기준 정의 |
| 상태 | 초안 |

### 1.1 목적

본 시스템은 지정된 `document` 폴더의 문서를 수집·분석·검색 가능한 형태로 색인하고, 사용자의 자연어 질문에 문서에 근거한 답변을 제공하는 것을 목적으로 한다. 답변에는 사용자가 근거를 확인할 수 있도록 원문 출처와 위치 정보를 함께 제공한다.

### 1.2 배경

PDF, Word, 텍스트 등 여러 형식으로 보관된 문서는 일반 키워드 검색만으로 필요한 정보를 빠르게 찾기 어렵다. 본 시스템은 문서를 의미 단위로 검색하고 검색 결과를 대규모 언어 모델(LLM)에 제공함으로써, 문서에 기반한 정확하고 추적 가능한 질의응답 기능을 제공한다.

### 1.3 주요 용어

| 용어 | 정의 |
|---|---|
| RAG | 외부 지식 검색 결과를 LLM 입력에 포함하여 답변을 생성하는 방식 |
| 인덱싱 | 문서를 파싱하고 청크로 분할한 뒤 임베딩 및 메타데이터를 저장하는 과정 |
| 청크 | 검색과 답변 생성에 사용하는 문서의 일정 단위 |
| 임베딩 | 텍스트의 의미를 수치 벡터로 표현한 값 |
| 벡터 저장소 | 임베딩과 관련 메타데이터를 저장하고 유사도 검색을 수행하는 저장소 |
| 리랭킹 | 최초 검색된 후보 문서의 질문 관련도를 다시 평가하여 순서를 조정하는 과정 |
| 근거 문서 | 답변 생성 시 참고한 원문 또는 원문 청크 |
| 할루시네이션 | 근거 문서에 없거나 사실과 다른 내용을 모델이 생성하는 현상 |

## 2. 시스템 범위

### 2.1 포함 범위

- 지정된 `document` 폴더와 하위 폴더 탐색
- PDF 및 일반 문서의 텍스트 추출
- 스캔 PDF에 대한 OCR 확장 가능 구조
- 문서 정제, 청킹, 임베딩 및 색인
- 자연어 질문에 대한 관련 문서 검색
- 검색 결과에 기반한 답변 생성
- 파일명, 페이지 등 출처 정보 표시
- 신규·수정·삭제 문서의 재색인
- 오류 및 처리 상태 기록
- 검색 및 답변 품질 평가

### 2.2 제외 범위

다음 항목은 1차 버전에서 제외하며 별도 요구사항 승인 후 확장한다.

- 인터넷 검색 결과를 이용한 답변
- 문서 원본의 작성·편집 기능
- 이메일, 메신저, 클라우드 드라이브와의 실시간 연동
- 이미지·도표 자체에 대한 정밀한 시각 질의응답
- 음성 질문 및 음성 답변
- 복잡한 조직별 다중 권한 관리
- 모델 자체의 파인튜닝

### 2.3 전제 조건

- 문서 원본은 프로젝트에서 접근할 수 있는 `document` 폴더에 저장된다.
- 사용자는 문서를 열람할 권한이 있다.
- 암호화되거나 손상된 파일은 정상적으로 파싱되지 않을 수 있다.
- LLM과 임베딩 모델은 설정으로 교체할 수 있어야 한다.
- 외부 API 사용 시 네트워크 연결과 유효한 인증 정보가 제공되어야 한다.

## 3. 사용자 및 이용 시나리오

### 3.1 사용자 유형

| 사용자 | 주요 역할 |
|---|---|
| 일반 사용자 | 문서에 대해 질문하고 답변 및 출처를 확인하며, JSON 설정 파일을 통해 프로그램 설정 관리 |
| 개발자 | 시스템 개발, 테스트 및 유지보수에만 관여 |

### 3.2 대표 이용 시나리오

1. 일반 사용자가 필요에 따라 JSON 설정 파일을 수정한다.
2. 일반 사용자가 `document` 폴더에 문서를 추가·수정·삭제한다.
3. 프로그램이 자동으로 `document` 폴더를 탐색하고 파일별 MD5를 계산한다.
4. 프로그램이 현재 파일의 상대경로 및 MD5와 DB의 파일 MD5 테이블을 비교하여 신규·변경·삭제 파일을 식별한다.
5. 프로그램이 신규·변경 파일만 파싱하고 청크와 임베딩을 생성하며, 삭제 파일의 기존 색인을 제거한다.
6. 프로그램이 처리 결과에 맞게 파일 MD5 테이블을 갱신한다.
7. 사용자가 자연어로 질문한다.
8. 시스템이 질문과 관련된 문서 청크를 검색하고 필요 시 리랭킹한다.
9. LLM이 검색된 근거만을 우선 사용하여 답변한다.
10. 시스템이 답변과 함께 파일명, 페이지 또는 문서 내 위치를 표시한다.
11. 사용자는 출처를 확인하여 답변의 신뢰성을 검증한다.

## 4. 기능 요구사항

요구사항 우선순위는 다음과 같이 정의한다.

- **필수(Must)**: 1차 배포에 반드시 포함
- **권장(Should)**: 품질 향상을 위해 포함 권장
- **선택(Could)**: 이후 확장 가능

### 4.1 문서 수집 및 변경 감지

| ID | 요구사항 | 우선순위 | 검수 기준 |
|---|---|---|---|
| FR-ING-001 | 시스템은 설정된 `document` 폴더와 하위 폴더를 탐색해야 한다. | 필수 | 하위 폴더에 있는 지원 파일까지 목록화된다. |
| FR-ING-002 | 시스템은 확장자 및 실제 처리 가능 여부를 기준으로 지원 문서를 식별해야 한다. | 필수 | 지원·미지원 파일이 구분되고 미지원 파일은 오류 없이 건너뛴다. |
| FR-ING-003 | 프로그램은 `document` 폴더를 자동으로 검사하고 각 지원 파일의 MD5 해시를 계산해야 한다. | 필수 | 별도의 사용자 인덱싱 명령 없이 파일별 MD5가 계산된다. |
| FR-ING-004 | 프로그램은 파일의 상대경로와 현재 MD5를 DB의 파일 MD5 테이블과 비교하여 신규·변경·삭제 문서를 자동으로 판별해야 한다. | 필수 | DB에 없는 경로는 신규, 동일 경로에서 MD5가 다른 파일은 변경, DB에만 남은 경로는 삭제로 식별된다. |
| FR-ING-005 | 삭제된 원본 문서에 연결된 청크와 임베딩은 색인에서 제거되어야 한다. | 필수 | 삭제 후 검색 결과에 해당 문서가 나타나지 않는다. |
| FR-ING-006 | 일반 사용자는 파일별 처리 상태(대기, 처리 중, 완료, 실패, 제외)를 확인할 수 있어야 한다. | 권장 | 실행 결과에서 파일별 상태와 사유를 확인할 수 있다. |
| FR-ING-007 | 프로그램은 신규 또는 MD5가 변경된 파일만 다시 인덱싱하고 MD5가 동일한 파일은 재인덱싱하지 않아야 한다. | 필수 | 반복 검사 시 MD5가 동일한 파일의 파싱, 청킹 및 임베딩이 다시 수행되지 않는다. |
| FR-ING-008 | 파일의 인덱싱이 성공한 경우에만 해당 상대경로의 MD5와 인덱싱 정보를 DB에 반영해야 한다. | 필수 | 인덱싱 실패 파일의 MD5가 완료 상태로 저장되지 않으며 다음 검사에서 다시 처리된다. |
| FR-ING-009 | 변경 파일의 재인덱싱 시 기존 청크와 임베딩은 새 색인으로 일관되게 교체되어야 한다. | 필수 | 변경 전·후 청크가 검색 결과에 혼재하지 않는다. |

### 6.2 파일 MD5 테이블

파일 변경 감지 전용 DB 테이블은 최소한 다음 정보를 관리한다.

| 필드 | 필수 여부 | 설명 |
|---|---|---|
| `source_path` | 필수 | `document` 폴더 기준 상대경로이자 파일 식별 키 |
| `md5_hash` | 필수 | 마지막으로 인덱싱에 성공한 파일의 MD5 해시 |
| `indexed_at` | 필수 | 해당 MD5로 인덱싱을 완료한 시각 |
| `status` | 필수 | 인덱싱 완료 또는 실패 등 처리 상태 |
| `document_id` | 필수 | 색인 및 청크와 연결되는 문서 식별자 |

상대경로와 MD5 비교 결과에 따른 처리 규칙은 다음과 같다.

- 현재 폴더에만 존재하는 상대경로는 신규 파일로 처리한다.
- 양쪽에 상대경로가 존재하지만 MD5가 다르면 변경 파일로 처리한다.
- 상대경로와 MD5가 모두 같으면 인덱싱을 생략한다.
- DB에만 존재하는 상대경로는 삭제 파일로 처리하고 관련 색인을 제거한다.
- 인덱싱이 성공한 뒤에만 DB의 MD5와 완료 시각을 갱신한다.

### 6.3 청크 메타데이터

| 필드 | 필수 여부 | 설명 |
|---|---|---|
| `chunk_id` | 필수 | 청크 고유 식별자 |
| `document_id` | 필수 | 원본 문서 식별자 |
| `content` | 필수 | 정제된 청크 텍스트 |
| `chunk_index` | 필수 | 문서 내 청크 순번 |
| `page_number` | 조건부 | PDF 페이지 번호 |
| `sheet_name` | 조건부 | Excel 시트명 |
| `slide_number` | 조건부 | PowerPoint 슬라이드 번호 |
| `section_title` | 권장 | 장·절 또는 제목 |
| `embedding_model` | 필수 | 임베딩 모델 및 버전 |
| `embedding` | 필수 | 벡터 값 또는 저장소 내 참조 |

### 6.4 데이터 수명주기

- 프로그램은 `document` 폴더의 파일 상태와 DB의 MD5 테이블을 자동으로 동기화한다.
- 원본이 변경되면 기존 문서 버전의 청크를 새 버전과 혼합하지 않는다.
- 원본이 삭제되면 관련 색인도 제거한다.
- 색인 재구축 전 필요한 경우 백업을 생성한다.
- 사용자 질의, 답변 및 검색 로그는 보안 정책에 정한 기간만 보관한다.
- 테스트 문서와 운영 문서는 저장소 또는 네임스페이스를 분리한다.

## 7. 시스템 구성 요구사항

시스템은 다음 논리 구성요소를 가진다.

```text
document 폴더
      |
      v
[자동 파일 탐색] -> [MD5 계산/DB 대조]
      |
      v
[형식별 파서 및 OCR] -> [텍스트 정제/청킹]
                              |
                              v
                       [임베딩 생성]
                              |
                              v
                       [벡터 저장소]
                              ^
                              |
사용자 질문 -> [질의 처리] -> [검색/리랭킹] -> [프롬프트 구성] -> [LLM]
                                                           |
                                                           v
                                                  답변 + 출처
```

### 7.1 권장 모듈 경계

- `config`: 일반 사용자가 관리하는 JSON 설정 로드 및 검증
- `loaders`: 파일 탐색과 형식별 파서
- `processing`: 정제, 구조 보존 및 청킹
- `indexing`: MD5 테이블 기반 변경 감지, 임베딩 및 자동 색인 관리
- `retrieval`: 벡터·키워드 검색, 필터 및 리랭킹
- `generation`: 프롬프트 구성, LLM 호출 및 인용 생성
- `interfaces`: CLI, API 또는 웹 UI
- `evaluation`: 검색·답변 품질 평가
- `observability`: 로그, 지표 및 오류 추적

구체적인 프레임워크와 제품은 설계 단계에서 결정하며, 본 요구사항은 특정 벤더에 종속되지 않는다.

## 8. 외부 인터페이스 요구사항

### 8.1 질의 인터페이스

CLI는 논리적으로 다음 입력을 지원한다.

- 질문 문자열

응답은 다음 정보를 제공한다.

- 생성된 답변
- 출처 목록
- 출처별 파일명과 원문 위치
- 근거 발췌문 또는 청크 식별자
- 처리 상태 및 오류
- 필요 시 처리 시간

## 9. 오류 처리 요구사항

| 오류 유형 | 기대 동작 |
|---|---|
| 지원하지 않는 파일 | 경고를 기록하고 제외 |
| 암호화 또는 손상 문서 | 실패 사유를 기록하고 다음 문서 처리 |
| 텍스트 없는 스캔 PDF | OCR 필요 상태 표시 또는 설정 시 OCR 수행 |
| 임베딩 API 제한·실패 | 제한 시간을 두고 재시도한 후 해당 배치를 실패 처리 |
| LLM API 실패 | 사용자에게 재시도 가능한 오류로 안내하고 요청 ID 기록 |
| 벡터 저장소 연결 실패 | 답변 생성을 중단하고 근거 없는 답변을 반환하지 않음 |
| 검색 결과 없음 | 문서에서 답을 찾지 못했다고 안내 |
| 잘못된 JSON 설정 | 애플리케이션 시작 시 JSON 문법, 필수 항목, 자료형 및 범위를 검증하고 잘못된 항목을 명확히 표시 |

## 10. 평가 및 시험 요구사항

### 10.1 시험 데이터

최소 다음 유형을 포함한 대표 문서 세트를 준비한다.

- 한국어 및 영어 PDF
- 여러 페이지로 구성된 PDF
- 제목, 문단 및 표가 포함된 DOCX
- TXT 및 Markdown
- 지원 시 XLSX와 PPTX
- 빈 파일, 손상 파일, 암호화 파일
- 스캔 PDF
- 서로 유사하거나 상충하는 내용을 가진 문서
- 문서 지시문 형태의 프롬프트 인젝션 샘플

### 10.2 평가 데이터셋

각 평가 항목은 질문, 기대 답변 핵심 요소, 정답 근거 위치, 답변 가능 여부를 포함한다.

- 단일 문서 내 사실 확인 질문
- 여러 문서를 종합해야 하는 질문
- 고유명사 및 정확한 숫자 검색 질문
- 표현은 다르지만 의미가 같은 질문
- 문서에 답이 없는 질문
- 모호하거나 범위가 넓은 질문
- 상충하는 문서가 존재하는 질문

### 10.3 시험 구분

| 시험 | 주요 검증 내용 |
|---|---|
| 단위 시험 | 형식별 파싱, 정제, 청킹, 해시, 메타데이터 생성 |
| 통합 시험 | 파일에서 벡터 저장소까지의 인덱싱 및 질의 흐름 |
| 회귀 시험 | 모델, 프롬프트, 청킹 또는 검색 설정 변경 전후 품질 비교 |
| 성능 시험 | 문서량별 인덱싱 시간, 검색 시간, 응답 시간, 메모리 사용량 |
| 보안 시험 | 비밀정보 노출, 경로 접근, 로그 마스킹, 프롬프트 인젝션 |
| 사용자 인수 시험 | 실제 업무 질문에 대한 답변 유용성과 출처 확인 가능성 |

## 11. 완료 및 인수 기준

다음 조건을 모두 충족하면 1차 버전의 개발이 완료된 것으로 판단한다.

- 필수 기능 요구사항이 구현되고 검수 기준을 통과한다.
- PDF, DOCX, TXT, Markdown 샘플 문서를 정상 인덱싱한다.
- 프로그램이 DB의 파일 MD5 테이블을 자동 대조하여 신규·수정·삭제 문서를 식별하고 색인에 올바르게 반영한다.
- MD5가 동일한 파일은 다시 파싱하거나 인덱싱하지 않는다.
- 일반 사용자가 JSON 설정 파일을 통해 주요 설정을 변경할 수 있다.
- 답변에 파일명과 페이지 등 확인 가능한 출처가 표시된다.
- 문서에 답이 없는 질문에 근거 없는 답변을 생성하지 않는다.
- 단일 문서 파싱 실패가 전체 인덱싱을 중단시키지 않는다.
- 필수 비기능 요구사항과 보안 요구사항을 충족한다.
- 자동화 테스트와 평가 결과가 기록된다.
- 설치, 설정, 인덱싱 및 질의 방법이 문서화된다.
- 목표 품질 지표는 승인된 평가 데이터셋에서 측정하고 결과를 공유한다.
